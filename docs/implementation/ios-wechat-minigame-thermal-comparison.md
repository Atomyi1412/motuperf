# iOS 微信小游戏内部热表现对比执行方案

Status: draft
Related requirements: [requirements/ios-wechat-minigame-thermal-comparison.md](../requirements/ios-wechat-minigame-thermal-comparison.md)

## 一、默认组织方式

- 1 名协调人：锁定配置、检查门禁、收集文件、判定无效轮次、汇总结论。
- 4 名执行人：每人固定一台核心设备和一个测试站，完整跑完该设备的“大神”/“时光杂货铺”数据。
- 只有 2 名执行人时分两批设备执行，不允许同一台设备中途换人或换测试站。
- 四台核心设备约产生 12 个设备小时的有效游戏运行（每台设备两款游戏各 90 分钟）；四站并行建议预留 1～1.5 个工作日，包含冷却、充电和重测。

## 二、设备分配

| 编号 | 设备 | 90 分钟综合场景顺序 |
| --- | --- | --- |
| D1 | iPhone 13 | 大神 → 时光杂货铺 |
| D2 | iPhone 12 Pro Max | 时光杂货铺 → 大神 |
| D3 | iPhone 11 | 大神 → 时光杂货铺 |
| D4 | iPhone X / iOS 16.8 | 时光杂货铺 → 大神 |

D5 iPhone 7 和 P1 iPad mini 6 仅在核心矩阵稳定后加入。第二台 iPhone X 仅做个体差异复核。

## 三、测试站准备

每个测试站准备：

- 同一版本的 MoTuPerf 安装包；会议记录版本号和 SHA-256。方案编写时跨平台源码版本为 `0.11.0`。
- 一台 Windows 电脑、固定 USB 端口、固定数据线。
- 指定 iPhone、同一 Wi-Fi 接入点和测试账号。
- 统一执行记录表和文件保存目录。

统一设置：

- 取下保护壳，不贴散热器，不使用风扇直吹。
- 屏幕亮度 50%，关闭自动亮度、True Tone、Night Shift。
- 媒体音量 30%，关闭蓝牙和蜂窝数据，仅使用指定 Wi-Fi。
- 开启勿扰模式，关闭自动更新和不必要的后台刷新，不录屏。
- 同一设备两款游戏使用同一微信版本；两款游戏资源提前更新完成，90 分钟综合场景保留首次加载和自然新手行为。
- 测试房间避免阳光直射和出风口直吹，空调设定建议 23±2°C；无室温计时必须在报告中标记环境温度证据不足。

## 四、设备预检

执行正式测试前，逐台记录：

| 字段 | 要求 |
| --- | --- |
| 设备编号/机型/iOS | 与飞书设备台账一致 |
| 电池健康度 | 80% 及以上进入核心；低于 80% 只作补充 |
| 维修状态 | 屏幕、电池或主板维修必须记录；不明则标记风险 |
| 微信版本 | 同设备“大神”/“时光杂货铺”保持一致 |
| MoTuPerf 版本/哈希 | 所有测试站一致 |
| USB 电脑/端口/线材 | 分配后固定 |
| 电池温度来源 | `pymobiledevice3-diagnostics-ioregistry` |
| 温度范围 | `device` |
| 10 分钟更新覆盖率 | 按实际温度轮询周期计算；当前约 5 秒一次，预计约 120 次，有效更新至少 108 次 |
| Thermal State | 记录可用/不可用，不可用不补零 |

预跑文件命名：`日期_设备编号_PRECHECK_执行人`。预跑不合格先排查连接和依赖；Battery Temperature 仍不可用则该设备退出温升排名。

## 五、试跑门禁

1. 使用 D1 与 D4，对“大神”和“时光杂货铺”各完成 1 次 90 分钟综合场景试跑；试跑数据默认不计入正式结果。
2. 验证 5 分钟基线、60/90 分钟分段标记、温度来源、5 秒轮询覆盖率、冷却、保存和文件命名。
3. 检查 60 分钟新手段和 30 分钟复杂段是否均完成，复杂段操作偏离是否在 60 秒以内。
4. 试跑发现流程或数据问题时先修订会议脚本；不得用试跑结果替代正式配对数据。
5. D1/D4 均无阻塞问题后，才开放 D1～D4 全量执行。

## 六、每次运行开始门禁

1. 设备电量达到 95%～100%，固定连接电脑 USB，不使用快充或无线充电。
2. 强制退出微信及其他前台应用，等待设备冷却。
3. 打开微信停留在非游戏页面，MoTuPerf 选择 `com.tencent.xin`，勾选 Screenshot、FPS、FrameTime/Jank、Memory、CPU、Device Temperature、Thermal State。
4. 开始采集后先记录 5 分钟空闲基线。
5. 最近 5 分钟 Battery Temperature 极差不超过 0.5°C，最后 3 分钟中位数处于该设备当天参考基线 ±0.5°C。
6. Thermal State 可用时必须为 `0 nominal`；不可用时记录 `N/A`。
7. 协调人或执行人确认门禁通过后，记录“进入游戏时间”，再执行会议脚本。

## 七、90 分钟连续综合场景

- “大神”和“时光杂货铺”各运行 90 分钟，使用新账号或首次进度。
- 0～60 分钟：自然跟随新手引导和正常内容，不为制造高负载反复进入非自然场景。
- 60～90 分钟：按会议脚本 V1 执行复杂/高负载玩法，记录进入复杂段的准确时间。
- 在 10、30、60、75、90 分钟核对采集状态；60 分钟节点必须记录分段标记。
- 两款游戏不要求内容完全相同，但复杂段的目标帧率、画质和操作频率应尽量相近。
- 复杂段受前 60 分钟热历史影响，只作为连续综合场景中的热态观察，不单独下严格场景结论。

## 八、冷却与下一款游戏

1. 保存本次 90 分钟运行的 `.motuperf`、CSV 和执行记录后，退出游戏并关闭微信。
2. 保持同一电脑、端口、线材和房间条件，不用冰袋、冰箱、风扇或其他主动降温手段。
3. 至少静置 15 分钟。
4. Battery Temperature 回到当天参考基线 ±0.5°C，最近 5 分钟极差不超过 0.5°C；Thermal State 可用时恢复 `0 nominal`。
5. 45 分钟仍未恢复则停止该设备当天的第二款游戏测试，后续另行安排。

## 九、文件命名与记录

目录：`日期/设备编号/场景/`。

文件名：

```text
YYYYMMDD_设备编号_大神或时光杂货铺_COMPOSITE90_顺序_执行人
```

每次 90 分钟运行记录至少包含：

| 类别 | 字段 |
| --- | --- |
| 身份 | 日期、执行人、设备编号、机型、iOS |
| 软件 | 微信版本、MoTuPerf 版本/哈希、游戏版本/构建 |
| 环境 | 房间、空调设定、网络、电脑、USB 端口、线材 |
| 初始状态 | 电量、电池健康度、T0、Thermal State、亮度、音量 |
| 场景 | 游戏“大神”/“时光杂货铺”、90 分钟综合场景、60/90 分钟分段、顺序、实际开始/结束时间 |
| 结果 | T_60、T_end、T_max、DeltaT_60、DeltaT_complex、DeltaT_end、DeltaT_max、RiseRate_10m、Thermal State |
| 性能 | FPS、FrameTime/Jank 质量、CPU、内存 |
| 观察 | 主观触感、偏离、异常、有效/无效及原因 |
| 证据 | `.motuperf`、CSV 文件名 |

公共报告和文件名不写完整 UDID、手机号、账号密码。

## 十、数据计算

只读取满足以下条件的温度行：

- `Temperature-Battery[C]` 有数值。
- `Temperature Updated=true`。
- `TemperatureSource=pymobiledevice3-diagnostics-ioregistry`。
- `TemperatureScope=device`。

计算：

- `T0`：进入游戏前最后 3 分钟有效温度中位数。
- `T_60`：第 60 分钟节点前后 30 秒有效温度中位数。
- `T_end`：第 90 分钟结束前最后 5 分钟有效温度平均值。
- `T_max`：90 分钟游戏阶段最高有效温度。
- `DeltaT_60 = T_60 - T0`；`DeltaT_end = T_end - T0`；`DeltaT_max = T_max - T0`。
- `DeltaT_complex = T_end - T_60`：后 30 分钟复杂段的增量温升，不解释为独立场景温升。
- `RiseRate_10m = (第10分钟温度 - T0) / 10`。
- Thermal State：最高等级、首次升档时间、非 `nominal` 时长占比。

FPS、FrameTime/Jank、CPU 和内存用于解释温升。Jank 只有在 MoTuPerf 标记为可靠有序帧、目标归因成立时参与正式比较；否则写 `N/A`。

## 十一、主观触感

统一在每次 90 分钟运行结束后立即记录：

- 0：无明显热感。
- 1：轻微温热，不影响操作。
- 2：明显温热，持续可感知。
- 3：较热，影响长时间握持。
- 4：烫手或不适，需要停止。

触感只放在补充观察，不参与温度排名。

## 十二、无效与终止

以下情况该次 90 分钟运行无效，原始文件仍须保存：

- 以实际温度轮询周期（当前约 5 秒）计算，有效温度更新数/预期轮询数不足 90%，来源或范围不符；不得用全部 CSV 行数作为分母。
- 起始温度、Thermal State 或电量不满足门禁。
- 更换电脑、USB 端口、线材或执行人员。
- 来电、系统更新、明显后台下载、网络中断、崩溃或任一分段脚本偏离超过 60 秒。
- 目标 PID 漂移，导致 CPU/内存数据无法解释。

出现 Thermal State `3 critical`、系统温度警告、设备异常重启或测试人员感觉不安全时立即停止。

## 十三、结果判定

按设备比较两款游戏各 1 次 90 分钟综合场景配对：

- **自研内部热表现更高（设备内观察）**：`DeltaT_max(大神)-DeltaT_max(时光杂货铺) >= 1.0°C`，且两次运行均有效；可同时参考 `DeltaT_60`、`DeltaT_complex` 和 Thermal State。
- **未观察到明显差异**：90 分钟最大温升差绝对值小于 1.0°C，且 Thermal State、复杂段增量温升没有明显单向劣化。
- **结果不确定**：任一运行无效、基线不满足、90 分钟未完成、温度数据缺失，或复杂段操作偏离会议脚本超过 60 秒。

1.0°C 是单次配对的工程参考阈值，不代表统计显著性；本轮不据此推断所有设备或所有用户场景。

报告必须分别展示 0～60 分钟新手段、60～90 分钟复杂段和全程 90 分钟温升曲线；复杂段只作为热态观察，不单独形成严格场景结论。

## 十四、会议只需确认的事项

1. 游戏“大神”、游戏“时光杂货铺”和账号准备。
2. 统一画质、目标帧率、60 分钟新手段和 30 分钟复杂段脚本 V1。
3. 四名执行人、一名协调人、正式日期。
4. D5/P1 是否加入。
5. 同一 MoTuPerf 安装包版本与 SHA-256。

其余设备、环境、基线、冷却、顺序、保存、无效和判定规则按本文执行。

## 十五、最终报告结构

1. 测试目标与“设备内部热表现”结论边界。
2. 设备、软件、环境、USB 连接和数据来源。
3. 有效/无效样本数量及排除原因。
4. 每台设备两款游戏 90 分钟综合场景的分段温升、Thermal State 和性能伴随指标。
5. 每台设备的“更高/未观察到稳定差异/不确定”结论。
6. 0～60 分钟新手段、60～90 分钟复杂段曲线与主观触感补充。
7. 无表面温度、USB 充电、旧设备电池健康度和场景差异限制。
8. 是否需要性能优化、补测、热像仪/接触式探头复核的后续动作。
