# MoTuPerf 版本更新总结报告

## 一、报告概况

- **版本范围**：`v0.4.62` 至 `v0.10.1`
- **报告日期**：2026-08-28
- **当前最新版本**：`v0.10.1`
- **适用对象**：测试团队、项目负责人、内部试用人员
- **更新主线**：从 Windows WPF 单平台版本升级为 Windows 与 macOS 共用的 Avalonia 桌面版本，同时持续提高 Android/iOS 指标真实性、设备适配能力和界面可用性。

## 二、总体结论

本阶段完成了 MoTuPerf 从 Windows 专用工具向跨平台桌面工具的核心迁移。原 WPF `v0.4.65` 已作为稳定基线完整保留，新版使用 `.NET 8 + Avalonia`，Windows 与 Apple Silicon macOS 共用界面、采集逻辑、现场文件和导出语义。

主要成果包括：

1. 增加 iOS Thermal State 与 Android Thermal Status，补齐设备热状态观察能力。
2. 修复 Android 10 原生 APP、Android 微信小游戏的 Jank、BigJank 和 FrameTime 缺失问题。
3. 保持微信小游戏严格 PID 归因，避免同 UID 兄弟进程之间串采数据。
4. 完成设备、APP、进程选择，启动 APP，实时曲线，截图联动，现场保存/打开和 CSV 导出的跨平台迁移。
5. 完成参数面板、滚动条、图例、按钮状态、二级窗口和标题栏的系统性界面优化。
6. 增加黑暗、明亮和绿色三套主题，并形成可继续扩展的主题注册机制。
7. 生成 `v0.10.1` Windows x64 自包含安装包，内置 .NET、Python/iOS 依赖、ADB 和采集脚本。

### 2. 跨平台基础迁移

跨平台版本将原 WPF 界面迁移到 Avalonia，并继续复用经过验证的采集器、统计、进程匹配和数据模型。迁移期间完成了以下基础能力：

- 支持 Windows x64 与 Apple Silicon macOS `osx-arm64`。
- 保留设备、APP、进程检测、推荐、搜索、启动和选择流程。
- 保留 Screenshot、FPS、Jank、BigJank、Display FrameTime、进程内存、进程 CPU、设备温度和 Thermal State。
- 保留实时数据、选中数据、时间游标联动、截图缩略图和大图查看。
- 保留 `.motuperf` 现场文件及 CSV 导出，并兼容已有 session v1-v5。
- 不恢复模拟数据；指标不可用时显示不可用，不用零值或插值制造完整结果。

## 四、核心能力变化

### 1. 数据真实性与准确性

- FPS、FrameTime 和 Jank 优先使用有序显示帧时间戳，不根据目标工具结果硬凑公式。
- FPS 为真实 `0` 时保留为有效采样点，曲线可以连接到零值。
- 缺少真实有序帧源时，不伪造 Jank、BigJank 或 FrameTime。
- Android 原生 APP 可使用明确的 PID 或 UID/appId 图层归属；微信小游戏不能仅凭共享 UID 归属，仍要求精确 PID/进程/Surface 唯一匹配。
- FrameTime 只绘制真正发生帧更新的样本，温度、CPU、内存或 Thermal State 状态快照不会插入 FrameTime 曲线。
- 进程 CPU、内存等进程指标继续绑定所选 PID；设备温度和热状态明确标记为设备级指标。

### 2. 操作与分析效率

- 设备、APP、进程统一在二级窗口选择，并支持刷新、搜索、推荐和启动 APP。
- 采集期间禁止重新选择设备及应用，避免目标进程发生漂移。
- 实时数据持续刷新；用户选中历史时刻后，选中数据和截图保持固定。
- 点击或拖动任一曲线可联动其他曲线和截图时间线。
- 多序列指标支持点击图例单独隐藏或恢复曲线。
- 截图支持缩略图、双击大图、缩放和相邻截图切换。
- 停止、设备断开和退出采集流程保留保存询问；现场文件可恢复曲线、截图和选择状态。

### 3. 界面和主题

- 参数面板重新按旧 WPF 工作台的密度和层级组织。
- 指标选择收敛为截图、FPS、Display FrameTime、进程内存、进程 CPU、设备温度和 Thermal State 七个主项；Jank/BigJank 跟随 FPS，归一化/逐核 CPU 跟随进程 CPU。
- 统一按钮悬浮、按下、选中、禁用状态，避免 Fluent 默认黑底破坏视觉一致性。
- 统一纵向和横向滚动条、参数分割线、方形图例和二级窗口边框。
- 提供黑暗、明亮、绿色三个主题；主题只影响显示，不进入现场文件，不改变指标和导出数据。

## 七、风险与限制

1. Android 厂商对 SurfaceFlinger、thermalservice 和截图接口存在定制，新增设备仍可能需要补充兼容样本。
2. iOS 17+ 的 RSD、Developer Mode、DDI 和配对状态会影响进程、截图和指标采集，需在界面提示中继续保持明确诊断。
3. Thermal State/Thermal Status 是系统热等级，不等同于 CPU 或 GPU 的实际摄氏温度。
4. 当前 Windows 安装包未签名，其他电脑运行时可能出现 Windows 安全提示。
5. macOS 目前只完成交叉构建证据，不能据此宣称 Mac 真实设备链路已经全部可用。

## 八、后续建议

1. 使用 `v0.10.1` 在至少两台非开发电脑完成 Windows 安装和 Android/iOS 真机回归。
2. 建立固定设备矩阵，至少覆盖 Android 10、Android 新版本、微信小游戏、原生高刷新率游戏、iOS 16 及 iOS 17+。
3. 在 M 系列 Mac 上完成正式 `.dmg` 构建和真机验收，再决定是否对同事开放 Mac 版本。
4. 申请 Windows 代码签名证书；Mac 公开分发前完成 Developer ID 签名和 Apple 公证。
5. 后续每次发布保持版本、安装包、SHA-256、自动测试、真机型号和未完成验收项同时记录。

## 九、结论

`v0.4.62` 至 `v0.10.1` 的更新不只是界面换代，而是完成了采集工具的跨平台架构迁移、Android/iOS 热状态补充、旧 Android 帧指标兼容、微信小游戏 PID 归因强化、历史时刻联动分析以及可扩展主题体系建设。

当前 `v0.10.1` 已具备 Windows 内部安装试用条件。Windows 多电脑真机验证、商业签名和真实 M 系列 Mac 完整验收仍是正式扩大分发前的主要门禁。
