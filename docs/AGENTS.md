# docs 工作规则

本目录是项目知识库，所有需求、实现计划、资料摘要和术语沉淀默认使用中文。

## 基本原则

- 先澄清，再实现。遇到会改变产品边界、数据语义或技术路线的问题，必须先写入需求或实现文档并等待确认。
- 保持简单。第一版只服务 iOS USB 性能采集、实时曲线和本地导出，不扩展云端、多设备并发或完整报告体系。
- 小步修改。每次代码变更都必须能追溯到 `docs/requirements/` 和 `docs/implementation/` 中的需求或实现步骤。
- 验证优先。完成前必须运行能证明当前改动有效的本地检查；如果缺少真实 iOS 设备，必须明确标注真实采集未验证。

## 文档位置

- `docs/CONTEXT.md`: 术语表，只放领域术语和边界，不放实现细节。
- `docs/requirements/`: 需求文档，描述要解决什么和如何验收。
- `docs/implementation/`: 实现文档，描述最小可行实现和验证计划。
- `docs/wiki/sources/`: 外部资料或参考产品摘要。
- `docs/raw/`: 原始资料，只读保存，不直接改写。
- `docs/wiki/log.md`: 记录重要资料摄取、决策、验证和阻塞。

## 当前关键门禁

在开始编写应用代码前，需要确认：

- 第一版微信小游戏性能是否按 `com.tencent.xin` 微信宿主进程和系统可见 FPS/Jank/Memory 来采集。
- 第一版实现形态是否采用“本地 Web 操作台 + Python 后端”，后续再考虑原生桌面封装。

如果用户直接回复“确认”，即可把对应需求和实现文档状态从 `draft` 调整为 `confirmed` 并进入编码。
